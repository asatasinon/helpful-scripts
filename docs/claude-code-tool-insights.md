# Claude Code Agent 构建经验：Action Space（工具空间）设计心得

**作者**：Thariq (@trq212)  
**日期**：2026 年 2 月 27 日  
**来源**：X 帖子

## 引言：构建 Agent 最难的部分

构建 Agent Harness（代理框架）最困难的部分之一，就是**构造它的 Action Space（操作空间 / 工具空间）**。

Claude 通过 Tool Calling（工具调用）来执行操作。Claude API 提供了多种工具构造方式，包括 bash、skills、code execution 等原语。

面对这些选项，我们需要思考：
- 是只需要 1 个超级强大的工具（如 code execution 或 bash）就够了？
- 还是要准备 50 个工具，覆盖所有可能的使用场景？

**设计框架**：把自己代入模型的视角。

想象你正在解决一道困难的数学题，你希望拥有什么工具？
- 纸笔 → 最基础，但手动计算很慢
- 计算器 → 更好，但需要知道如何操作高级功能
- 计算机 + 编程能力 → 最强大，但需要会写代码和执行

**核心原则**：给 Agent 的工具必须**匹配它的真实能力**。  
要知道模型真正具备什么能力，只能通过**持续观察输出、反复实验、迭代**，学会 **“像 Agent 一样思考”（See like an agent）**。

以下是我们在构建 Claude Code 过程中，通过仔细观察 Claude 而总结的几条重要经验。

## 经验 1：提升提问能力（Elicitation）—— AskUserQuestion Tool

**问题**：Claude 用纯文本提问时，用户回答过程摩擦大、耗时。

**尝试 1**：在 ExitPlanTool 中增加问题数组  
→ 失败。计划和问题混在一起会导致逻辑冲突（用户答案可能与计划矛盾，是否需要调用两次？）。

**尝试 2**：修改输出格式为特定 Markdown（带选项的 bullet list）  
→ 部分有效，但 Claude 经常额外添加文字、遗漏选项、不严格遵守格式。

**最终方案**：创建 **AskUserQuestion Tool**  
- Claude 可在任意时刻调用，尤其在 Plan Mode 时特别提示使用。  
- 调用后弹出 Modal（模态框）展示结构化问题，并阻塞 Agent 循环直到用户回答。  
- 优点：
  - 强制结构化输出
  - 方便提供多个选项
  - 支持在 Agent SDK 或 Skills 中复用
  - Claude 非常愿意调用，输出稳定可靠

**关键启示**：再好的工具，如果模型不会自然地调用它，就毫无用处。

## 经验 2：随模型能力迭代工具 —— 从 Todo 到 Task

**早期阶段**：模型容易忘记任务 → 引入 **TodoWrite Tool**，并每 5 轮插入系统提醒。

**模型能力提升后**（尤其是 Opus 4.5）：
- Todo 列表反而成为限制（模型认为必须严格遵守，不能修改）
- 子 Agent（subagents）协同工作时，Todo 不支持依赖关系和共享更新

**升级方案**：替换为 **Task Tool**
- 支持任务依赖关系
- 支持子 Agent 之间共享更新
- 允许自由增删修改

**用途转变**：从“约束模型别跑偏” → “帮助多 Agent 协作”。

**启示**：随着模型能力提升，旧工具可能从帮助变为束缚。必须**持续审视工具的必要性**，并保持所支持的模型能力曲线相对一致。

## 经验 3：搜索接口设计 —— 从 RAG 到 Progressive Disclosure（渐进式披露）

**早期**：使用 RAG 向量数据库被动注入上下文  
→ 需要索引、环境脆弱，且上下文是“被给予”的而非 Agent 主动构建。

**升级路径**：
- 引入 **Grep Tool**：让 Claude 自己搜索代码库，主动构建上下文。
- **Agent Skills** 机制：通过 Markdown 文件实现 **Progressive Disclosure（渐进式披露）**。
  - Claude 先读取 Skill 文件
  - 文件可递归引用其他文件
  - 层层挖掘精确需要的上下文

常见用法：把 API 使用说明、数据库查询方法等写成 Skill 文件，按需读取。

**成果**：Claude 从“不会自己找上下文”进化到“能跨多层文件嵌套搜索”。

**扩展案例**：Claude Code Guide 子 Agent
- 问题：直接把所有文档塞进 System Prompt → 上下文污染，且很少被问到。
- 方案：给主 Agent 一个文档链接 + 专精搜索文档的 **Guide 子 Agent**。
- 优点：不污染主上下文，按需加载，仅在用户询问“How to use Claude Code”时触发。

**核心价值**：**Progressive Disclosure 是神器**。不要一次性塞满上下文，让 Agent 自己探索、逐步发现。

目前 Claude Code 维持在 **约 20 个工具**，新增工具的门槛非常高。

## 结语：工具设计是一门艺术，而非科学

工具设计没有一套死板的规则。它高度依赖：
- 具体使用的模型
- Agent 的目标
- 运行环境

**核心方法**：
- 多实验
- 多阅读模型输出
- 多迭代
- 学会 **“像 Agent 一样思考”（See like an agent）**

---

## 经验总结（核心 Takeaways）

1. **匹配模型真实能力**  
   不要凭空假设 Agent 需要什么工具，要通过持续观察和实验来发现它的能力边界。

2. **工具要“少而精”**  
   50 个工具会让模型困惑并浪费 token。宁可工具少、命名自然、语义清晰。

3. **持续迭代工具**  
   模型能力提升后，旧工具可能变成限制（Todo → Task）。敢于替换，甚至用子 Agent + Progressive Disclosure 替代新增工具。

4. **Progressive Disclosure 是王道**  
   不要把所有知识塞进 prompt 或 RAG，让 Agent 通过文件系统、Skills、子 Agent 自己层层探索上下文，既干净又高效。

5. **结构化用户交互（Elicitation）**  
   专用工具（如 AskUserQuestion）比纯文本提问更高效，能显著降低交互摩擦。

6. **搜索能力是 Agent 核心竞争力**  
   从被动 RAG → 主动 Grep + 递归搜索 + Skill 文件，是 Agent 能力的重要飞跃。

7. **整体哲学**  
   Agent 工具设计本质上是“赋予权限”的过程。  
   你给它什么权限，它就成为什么角色。  
   不断“See like an agent”，才能打造真正好用的 Agent 框架。

这份经验对任何希望构建高质量 AI Agent（尤其是基于 Claude 或类似大模型）的开发者都非常有参考价值。

**核心思想**：以**模型为中心**，而非以人类直觉为中心，不断迭代工具空间。
